# 재고 업무 정합성과 장애 복구

## 프로젝트 요약

동시 출고, 중복 요청과 외부 반영 직후의 장애가 전표·재고·분개를 어긋나게 할 수 있다는 문제를 다뤘다. Java, Spring Boot, MyBatis와 Oracle을 사용해 출고·부분 반품·단순 역분개를 구현하고, 트랜잭션과 outbox를 통해 업무 저장과 외부 전달의 실패 경계를 분리했다. 이 프로젝트는 백엔드와 데이터 신뢰성에 집중하며 별도의 프론트엔드는 만들지 않았다.

## 설계와 판단

- 창고·SKU 순서로 재고 행을 잠그고 수량을 검사해 동일 규약을 따르는 출고 요청이 가용 수량을 넘지 못하도록 했다. 전표·현재고·수불·단순 분개·outbox를 한 트랜잭션에 기록한다.
- 반품은 원출고를 참조하는 새 전표로 만들고, 누적 반품 수량과 금액을 제한해 전량 반환 시 원금액을 상쇄한다. 도메인 객체의 상태·금액 검증과 DB의 동시성 제어는 서로 다른 책임으로 분리했다.
- 요청 키와 입력 fingerprint로 재시도를 구분한다. 외부 전달은 최소 한 번 시도하고, 최종 중복 방지는 모의 수신자가 이벤트 ID를 기준으로 처리하도록 했다. 이를 무조건적인 exactly-once로 표현하지 않는다.

## 검증과 결과

- 로컬 Oracle에서 재고 60개에 동시 출고 100건을 요청해 60건 확정·40건 거절됐다. 같은 키의 동시 요청 40건은 전표 1건으로 귀결됐고, 출고 3개에 대한 동시 반품 20건은 3건 확정·17건 거절됐다.
- 선택한 출고 12개·반품 11개 저장 경계에서 실패를 주입해 롤백과 동일 요청 재시도를 확인했다.
- 외부 모의 수신 직후 실제 작업자 JVM을 강제 종료하고 재시작한 실험에서, 3회 모두 전달 2회·외부 반영 1회·수불/현재고 일치를 확인했다. 관찰 복구 시간은 약 6.5~6.6초이며 5초 lease와 JVM 기동이 포함된 소표본이다.
- 실제 재고 보고서 SQL의 가상 수불 10만 행 비교에서 후보 인덱스 적용 후 p95가 **0.840ms → 0.453ms, 46.1% 감소**했다. 별도 새 컨테이너에서 반복한 결과는 0.695ms → 0.428ms, 38.4% 감소였다. 각 실제 실행 커서의 마지막 1회 버퍼 접근은 58 → 20이었다. 후보 인덱스는 선택 적용이며 쓰기 비용은 미측정이다.

## 범위와 한계

수치는 로컬 컨테이너의 가상 입력 기준이다. 조회 arm의 캐시·공유 호스트 부하는 완전히 통제하지 않았고 복구 시간은 3회 관찰값이다. 외부 시스템은 모의 수신자다. 전체 writer의 잠금 준수, tenant 격리, 운영 보안·부하, 실제 ERP 연동이나 완전한 회계 기능은 검증하지 않았다. 별도 조회로 얻은 내부·외부 상태는 하나의 원자적 스냅샷이 아니다.

조건·원시 표본·코드 경로는 [측정 결과](../RESULTS.md), 재현 절차는 [Oracle 구현 안내](oracle-workflow.md)에 기록한다. 기존 PostgreSQL 비교 수치는 별도 실험이며 Oracle의 전후 결과와 섞지 않는다.

# 재고 업무 정합성과 운영 신뢰성 계획

- 상태: 진행 중. 목표와 수용 기준은 구현이나 측정 완료를 뜻하지 않는다. 실제 완료 및 미검증 범위는 [Oracle 구현 안내](../oracle-workflow.md)와 [측정 결과](../../RESULTS.md)를 따른다.
- 대상: Java 기반 개인 재고 업무 시스템. 기존 저장소의 PostgreSQL 실험과 원시 결과는 보존한다.
- 핵심 질문: 동시 요청, 중복 요청, 반품 및 부분 실패가 발생해도 전표·재고·회계 기록을 추적하고 대사할 수 있는가?
- 범위: 주문 확정부터 출고·재고 이동·단순 매출/채권 기록, 부분 반품·역분개, 보고와 모의 외부 전달까지의 수직 흐름.

## 1. 현재 상태와 경계

기존 PostgreSQL 구현은 MyBatis와 `JdbcTemplate`을 함께 사용한다. 요청 접수, 선택적 재고 writer, 모의 외부 전달과 outbox 처리가 한 서비스에 집중돼 있다. 기본 요청은 재고 writer와 매핑 검사가 활성화된 업무 흐름이 아니므로, 단순 접수 성공을 재고 반영 완료로 해석하지 않는다. 별도의 Oracle 프로파일에는 Java 도메인 객체, MyBatis 저장, 출고·부분 반품, 단순 분개·보고 및 outbox 경로를 추가했다.

기존 격리 환경의 동시 출고·중복 요청·모의 대상 장애 실험과 한계는 [RESULTS.md](../../RESULTS.md)에 남긴다. 재고 보호는 같은 잠금 규약에 참여하는 writer 범위에 한정된다. 현재 대사는 요청 키와 건수 중심이며 수량·금액 대사가 아니다. 외부 대상은 모의 서비스이고, 실서비스 연동이나 운영 SLA를 검증한 것이 아니다.

Oracle 경로는 격리 DB에서 검증 중이며 전체 업무·운영 시스템은 아니다. 정적 역할 토큰은 개발용이고 전체 writer 통합 및 tenant 격리는 구현하지 않았다. PostgreSQL 측정 결과를 Oracle 측정 결과로 표현하지 않는다.

## 2. 범위와 우선순위

| 순서 | 딥다이브 | 핵심 결과물 |
| --- | --- | --- |
| 1 | Java 업무 모델과 정합성 | 주문·출고·부분 반품·역분개, 객체 책임, 트랜잭션과 동시성 검증 |
| 2 | Oracle·MyBatis 데이터 설계와 조회 | 업무 테이블·제약조건, 재고/매출/채권 대사, 쿼리와 인덱스 비교 |
| 3 | 장애 복구와 운영 | 업무 기록과 outbox의 원자성, 재처리, 수량·금액 대사, 이력과 최소 권한 |

Oracle 실행 가능성을 먼저 확인한 뒤 1과 2를 작은 수직 단위로 함께 진행한다. 실제 구현에서 우선 순위는 출고와 재고 정합성, 부분 반품, 단순 회계 역분개, 조회, 운영 복구다. 기능 확장보다 앞 단계의 검증을 우선한다.

### 이번 범위에서 제외

- 실제 외부 ERP API 연결, 실제 고객 데이터 또는 실제 운영 성과 주장.
- 세금·수금·기간 마감·원가 평가·다중 통화 등 완전한 회계 시스템.
- 범용 다중 tenant 격리, 전체 조직 권한 체계, 프론트엔드 전면 구현.
- 재고 조정·창고 간 이동·대량 업로드의 전체 업무 구현. 기존 문제 목록에서 삭제하는 것이 아니라 이번 수직 흐름 다음 단계로 둔다.
- 캐시, 메시지 브로커, 분산 인프라를 기술 자체의 사용을 위해 도입하는 일. 측정과 필요성이 확인될 때 별도 결정한다.

## 3. 공통 업무 계약

### 상태와 원본 보존

- 출고 전표는 `DRAFT → CONFIRMED → POSTED` 상태를 가진다. `DRAFT`와 `CONFIRMED`에서는 재고·회계에 반영하지 않고, `POSTED` 전환 시 업무 기록을 원자적으로 반영한다. 전이를 생략하거나 되돌리는 동작은 허용된 명시적 명령으로만 수행한다.
- 반품은 원출고 항목을 참조하는 별도 전표로 기록한다. 부분 반품이므로 원출고를 첫 반품에서 전체 역분개 상태로 바꾸지 않는다. 전체 반환 여부는 확정된 누적 반품량으로 판단한다.
- 전액 취소가 필요한 경우에도 원거래를 삭제하거나 덮어쓰지 않고 원출고를 참조하는 반대 기록으로 표현한다. 반품과 전액 취소는 같은 원출고의 반환 가능 수량을 공유한다.
- 반품은 이미 확정된 출고에만 허용한다. 같은 원출고 항목의 누적 확정 반품량은 원출고량 이하여야 하며, 동일 상품·단위와 원출고 금액을 기준으로 계산한다.
- 1차 회계는 단일 통화, 세금·수금 없는 매출/채권의 단순 기록과 반대 분개로 한정한다. 금액 정밀도·반올림 규칙을 명시하고, 여러 번 부분 반품한 뒤 전량 반환 시 누적 역분개 금액이 원금액을 초과하지 않고 정확히 상쇄되게 한다.

### 정합성과 중복 요청

1. 재고 식별자는 최소 창고와 SKU를 포함하며, 출고 후 재고는 음수가 될 수 없다.
2. 출고 확정은 전표 상태, 전표 항목, 재고 수불 및 현재고, 단순 매출·채권 기록과 outbox를 같은 DB 트랜잭션으로 기록한다. 반품 확정도 원출고 참조, 반품 전표, 재고 복원, 역분개, outbox를 함께 기록한다.
3. 같은 멱등 키와 같은 정규화된 요청은 최초 결과를 반환하고, 같은 키에 다른 업무 입력은 충돌로 거절한다. 키의 유효 범위·보관 기간·정규화 방식을 구현 전에 명시한다.
4. 모든 관련 쓰기 경로가 동일한 제약과 잠금 규약을 따라야 한다. 우회 경로가 남아 있으면 보장 범위를 해당 참여 경로로 제한하고 명시한다.
5. 동시 부분 반품은 원출고 항목별 반환 가능량을 DB에서 직렬화하거나 동등한 조건부 갱신으로 보호한다. 다중 SKU 잠금은 일관된 순서로 얻고 교착·대기 실패를 명시적으로 처리한다.
6. 업무 저장 성공과 외부 전달 완료는 구분한다. outbox가 보장하는 것은 원자적 기록과 재시도 기반 전달이며, 외부 중복 방지는 대상의 멱등 처리에 의존한다.

## 4. 딥다이브 1 — 객체지향 업무 모델과 트랜잭션

### 설계

- 출고 전표, 전표 항목, 반품, 수량과 금액 등의 객체에 상태 전이와 값 검증 책임을 둔다. 잘못된 상태나 음수 수량을 만들 수 있는 공개 변경을 제한한다.
- 응용 서비스는 명령 검증, 저장소 호출과 트랜잭션 경계를 조정한다. SQL, JSON 파싱, 외부 전송과 스케줄링은 도메인 판단에서 분리한다.
- 도메인 객체는 업무상 가능한지를 판단하되, 동시 요청 사이의 정합성은 Oracle의 잠금·조건부 갱신·제약조건과 트랜잭션으로 보장한다. 객체 검증만으로 동시성을 보장한다고 주장하지 않는다.
- 인터페이스와 추상화는 서로 다른 구현 또는 테스트 경계가 실제로 필요한 곳에만 둔다. 클래스 수나 디자인 패턴 개수는 품질 지표로 삼지 않는다.
- PostgreSQL 기존 writer와 신규 Oracle writer가 같은 데이터를 별도 규약으로 변경하는 중복 경로를 만들지 않는다. 기존 의미를 조사하고 호환 계약과 차이를 문서화한 후 안전한 경로를 결정한다.

### 검증 및 종료 조건

- 허용·금지 상태 전이, 잘못된 수량, 부분 반품 누적 한도, 금액 정밀도와 전량 상쇄를 도메인 단위 테스트로 검증한다.
- 동일 SKU 동시 출고, 중복 요청, 동일 원출고에 대한 동시 부분 반품을 실제 Oracle 통합 테스트로 검증한다.
- 각 저장 단계 사이 실패를 주입해 전표·수불·현재고·분개·outbox가 모두 롤백되는지 확인한다.
- 정상·실패 케이스별 요청과 최종 DB 상태를 비교하고, 원본 전표에서 반품과 역분개까지 역추적할 수 있어야 한다.

## 5. 딥다이브 2 — Oracle·MyBatis와 보고

### 환경과 데이터 설계

- 먼저 로컬 아키텍처, 실행 자원, 사용 가능한 Oracle 개발용 배포 방식과 드라이버·라이선스 조건을 확인한다. 실행되지 않으면 원인을 기록하고 Oracle 검증을 완료 처리하지 않는다. 기존 DB나 타 프로젝트 데이터를 삭제·덮어쓰지 않는 격리 환경을 사용한다.
- 주문·전표 헤더/항목, 재고 수불, 현재고, 단순 분개, 요청 키, outbox와 이력을 모델링한다. PK/FK, 수량과 상태 제약, 업무 식별키 유일성, 원거래 참조를 명시한다.
- 실제 업무에 쓰는 저장·조회 SQL을 MyBatis 매퍼로 구현한다. Oracle의 잠금, identity 또는 sequence, 날짜·정밀도·페이징 및 오류 처리를 해당 DB 기준으로 검증한다. PostgreSQL 전용 SQL을 그대로 이식했다고 가정하지 않는다.
- 스키마 변경은 버전 관리하고 빈 DB 초기화와 기존 테스트 데이터 보존을 모두 확인한다. 기존 PostgreSQL 실험과 원시 결과는 별도로 유지한다.

### 보고와 성능 실험

- 창고·SKU 현재고와 기간별 수불, 기간별 매출·채권, 원출고별 반품을 조회한다. 기초 재고가 있다면 명시적으로 수불에 반영한다.
- 같은 스냅샷 또는 일관된 기준 시각에서 수불 합계와 현재고, 확정 전표와 분개·보고 합계를 비교한다. 반품·역분개의 부호와 기준일을 기록한다.
- 가상 데이터의 행 수·분포·핫 SKU·조회 조건을 먼저 고정하고 baseline SQL, 실행계획, 인덱스 또는 쿼리 변경 후 동일 결과와 비용을 비교한다.
- 각 회차의 p50/p95, 표본 수, 처리량, 쿼리 수와 가능한 DB 측정값을 기록한다. warm-up, 반복 횟수, 캐시 상태, 하드웨어·DB 버전과 소스 식별자를 남긴다. 표본이 부족하면 p95를 유의미한 결과로 표현하지 않는다.

### 종료 조건

Oracle에서 빈 환경 초기화, MyBatis 업무 경로와 보고서 대사가 통과하고, 변경 전후 쿼리가 같은 결과를 반환해야 한다. 성능 향상이 없거나 악화되면 그 결과도 보존한다. 환경이 준비되지 않으면 미검증으로 명시한다.

## 6. 딥다이브 3 — 장애 복구와 운영

- 업무 확정과 outbox 기록을 동일 트랜잭션에 저장하고, 모의 대상 전송·처리 상태를 접수 결과와 구분한다.
- 정상 전송, 일시 오류, 대상 반영 후 응답 유실, worker 종료, 중복 전달, 최대 재시도 초과를 재현한다. 유실·중복을 대상의 실제 최종 상태로 확인한다.
- 재시도 횟수·지연·lease·최대 실패 후 상태와 수동 재처리 절차를 명시한다. 재처리는 원 요청과 연결하고 같은 키로 중복 적용되지 않게 한다.
- 전표 ID와 요청 키로 전표·수불·분개·전송 이력을 추적한다. 내부 수량·금액 대사와 모의 대상의 식별자·수량·금액 대사는 서로 구분한다. 대상이 제공하지 않는 값은 검증 불가로 표시한다.
- 최소한 조회자와 담당자의 권한을 구분하고 확정·반품·재처리와 보고 조회를 제한한다. 변경 주체·시각·결과를 기록하고, 권한 없는 요청과 감사 이력 기록 실패의 처리 방침을 테스트한다. 구현 전까지 기존 실험 API를 실제 데이터에 연결하거나 배포하지 않는다.

### 종료 조건

각 장애 시나리오의 최종 업무 상태와 전송 상태가 설명 가능하고, 정해진 재처리 후 대사 결과를 기록해야 한다. 모의 대상에 대한 결과를 실제 외부 ERP 성과로 표현하지 않는다.

## 7. 측정과 포트폴리오 근거

| 질문 | 측정 후보 | 비교 조건과 주의 |
| --- | --- | --- |
| 동시 출고·반품이 정합적인가 | 초과 확정 건수, 음수 재고, 반품 한도 위반, 수불/현재고 불일치 | 동일 SKU·수량·요청 수와 격리 DB 기준. 응답뿐 아니라 확정 행과 수량을 확인 |
| 중복·부분 실패를 복구하는가 | 중복 전표/반영, 누락·불일치 건수, 재처리 완료 시간 | 같은 장애와 논리 요청 수. 대상이 멱등성을 보장하는 범위 명시 |
| 조회가 개선됐는가 | p50/p95, 쿼리 수, 실행계획과 읽기량 | 같은 Oracle 버전·데이터·쿼리·환경에서 비교하고 결과 동등성 확인 |
| 권한과 추적이 동작하는가 | 역할별 허용/차단 테스트, 전표 추적·대사 성공 건수 | 테스트 시나리오와 분모 명시. 보안 전반에 대한 보증으로 확대하지 않음 |

개선율은 `((변경 전 - 변경 후) / 변경 전) × 100`으로 계산하되 기준값이 0이면 비율을 만들지 않고 절대 건수를 제시한다. 처리량처럼 큰 값이 좋은 지표는 방향을 명시한다. 기존 운영 경로가 아닌 비교용 취약 구현은 그 사실을 밝힌다.

원시 결과, 실행 명령, 입력 조건, 각 회차 결과, 실패 사례와 소스·스키마 식별자를 함께 남긴다. 기존 PostgreSQL synthetic 결과와 신규 Oracle synthetic 결과를 구분하며, DB가 다른 결과로 전후 개선율을 산출하지 않는다. 운영 트래픽·실사용자·실제 회사 도메인의 검증으로 표현하지 않는다.

## 8. 단계별 산출물과 완료 판정

1. **환경·기준선:** Oracle 실행 조건과 격리 여부 확인, 현행 경로·기존 결과 보존, 업무 계약 및 초기 비교 시나리오 기록.
2. **출고 수직 흐름:** 도메인 모델, Oracle/MyBatis 저장, 동시 출고·멱등성·롤백·대사 테스트.
3. **반품과 역분개:** 부분·전량 반품, 원거래 참조, 동시 반품 한도, 재고 복원·금액 상쇄 및 롤백 테스트.
4. **보고와 성능:** 수불·현재고·매출·채권 대사, 동일 결과를 보장하는 쿼리 전후 측정.
5. **복구와 접근 통제:** outbox 장애 주입·재처리, 업무 단위 대사·이력·최소 역할 검증.
6. **정리:** 재현 방법, 결과와 한계, 선택과 버린 대안, 미완료 사항을 문서화. 측정 결과가 없는 항목은 미측정으로 둔다.

완료는 테스트와 대사가 실제 대상 환경에서 통과하고 근거를 재현할 수 있을 때만 선언한다. 어느 단계가 막히면 가능한 독립 작업은 진행하되, 미검증 항목과 영향은 따로 기록한다.
